## Custom UI and ADS decision

Stay with React/Vite **Custom UI**. The [Forge Custom UI guidance](https://developer.atlassian.com/platform/forge/extend-ui-with-custom-options/) permits a custom front end within Forge's resource/CSP constraints; this is not a UI Kit migration. The [Forge theming guide](https://developer.atlassian.com/platform/forge/design-tokens-and-theming/) explicitly documents **`view.theme.enable()`** and token-backed CSS. Call it only in the Forge transport; do not make a standalone preview invoke a nonexistent host. Respect host theme changes and use documented `data-color-mode` behavior, not invented manipulation of internal theme attributes.

Use ADS white/neutral surfaces, semantic text/border/focus colors and spacing tokens. The olive identity recedes to a small brand mark/accent. No display serif, decorative poster, continuous animation or arbitrary new palette. Keep semantic headings, a roughly 24px page heading, 14px working text and readable record identifiers; use rem/token scales rather than shrinking a mobile UI to fit. The [ADS typography guidance](https://atlassian.design/foundations/typography/) names **Atlassian Sans** and **Atlassian Mono**, with system-font fallback for apps not yet using refreshed fonts. Use Sans for body/headings and Mono for identifiers where supported, remove Georgia/Times, and use the documented fallback when font delivery is unavailable. Check permitted font distribution and Forge CSP before choosing delivery; no external font host or license assumption. Verify actual rendered faces, not just a CSS family name. The current recorded faces are SF NS/Courier despite Inter appearing in CSS.

Proposed minimal direct packages, with publisher-registry metadata checked this turn: `@atlaskit/button` **25.8.1**, `@atlaskit/lozenge` **17.0.8**, `@atlaskit/flag` **19.0.5**, `@atlaskit/tokens` **20.12.0**. Their declared React peers include `^19.0.0`; no React downgrade is proposed. This establishes peer declarations, not a blanket Forge support guarantee. After approval, validate the exact versions' Vite/CSS output, CSP and bundle before retaining them. If a component cannot work within the existing supported resource/CSP, use one faithful, token-backed semantic HTML equivalent; document the specific incompatibility instead of inventing a new brand or bypassing policy. No full component-suite migration or dependency repair sprint is implied.

- [Button API](https://atlassian.design/components/button/code): use the current documented entry point/props, including `isDisabled`; one primary action per screen context. Native fields can use ADS tokens without adding an entire form library.
- [Lozenge API](https://atlassian.design/components/lozenge/code): preserve visible text. PASS → success; FAIL → danger; UNKNOWN/Potential/Uncertain → warning; Confirmed/Saved → information; Suggested → neutral. “Confirmed” means recorded association, not safe product. These mappings are our product decisions using documented appearances. Do not rely on color or a dot, truncate status words, or copy deprecated props from old examples.
- [Flag guidance](https://atlassian.design/components/flag): transient save/write confirmations only. Persistent transport context is a compact hint; persistent failures stay actionable inline/section messages. No fat environment flag on each screen and no auto-dismiss of a consequential error.

### Critical state and triage rules

The first-finding helper orders **FAIL → UNKNOWN → PASS**, preserving configured order within a state. It chooses a reachable recorded counterexample for inspection; no alternate scenario or node is invented. Cover the Northstar default, UNKNOWN-only configuration, all-PASS configuration, no applicable records, missing/unreachable references, duplicate references, changed datasets and saved-report reopening. If no recorded path exists, focus the finding and state that limit instead of displaying the source path as its answer.

Keep **selected finding**, **inspected record** and **anchored path target** distinct. Clicking a finding selects its record and path target. Clicking BATCH-101 while inspecting the SHIP-002 path changes the inspector, not the path destination. A new case resets invalid selection; ordinary navigation preserves it. Share assertion display wording while preserving existing engine title/result bytes and assertion IDs, because the saved analyst recomputes and compares results.

Triage is a **presentation projection** of the existing suggestions and receipts. FAIL groups first, then UNKNOWN; PASS is not a follow-up queue. Show the first few rows per group with an explicit expansion/count; mark zero-population UNKNOWN as “Not evaluated.” Expose failed/uncertain receipt status on the group even when collapsed. Existing created/uncertain actions cannot become unchecked fresh suggestions. Use structured finding identity, not truncated display text, to associate proposals; preserve the legacy de-duplication and ID order if extracting a shared helper. No global “10 open” surrogate for priority.

The analyst offers **Why did shipment-destination fail?**, **Which lots are UNKNOWN and why?**, and **What did the WH-NORTH hold change?** when applicable to the saved result. Do not label a PASS as a failure, offer nonexistent saved controls or use a shortened revision as action input. The target answer leads with the actual finding, gives a readable explanation with citations and directs proposed work to review. Its on-page fallback is clearly deterministic evidence, never a staged Rovo answer.
